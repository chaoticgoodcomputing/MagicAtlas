### G18 — no-maximum-hand-size (`mast-tdd/2026-07-10-no-maximum-hand-size`) — IMMUTABILITY / DESIGN CALL

**(a) Faithfulness of the scope values — PASS.** All 4 modified golds (Graceful Adept, Decanter of Endless Water, Spellbook, Niv-Mizzet Visionary) are verbatim "You have no maximum hand size." → `Player:{Kind:You}` is the faithful single-controller scope. All 5 `noMaxHandSize` fixtures on the branch carry the field — the required-field migration is complete, no latent deserialization break.

**(b) DESIGN CALL — RECOMMEND KEEPING `Player` REQUIRED (do NOT make it nullable-with-default).** Rationale:
1. **Precedent consistency.** The closest analogue, `CantGainLifeEffect` (a static player-scoped restriction, structurally identical: "You can't gain life" vs symmetric "Players can't gain life."), already uses `public required ObjectReference Player`. Making `NoMaxHandSizeEffect.Player` nullable would fork two structurally-identical effect families onto opposite conventions — a net inconsistency worse than the 4 gold edits.
2. **Explicit structure > implicit default.** MAST favors structural encoding of meaning. `null`-means-You is an undocumented convention every downstream consumer (PortWalk projection included) must special-case, and it conflates "scope is You" with "scope unspecified."
3. **The 4 gold edits are correct backfills, not test-weakening.** They add the true scope value; this is legitimate schema evolution, not a ratchet/baseline shrink (contrast the count-baseline immutability concern in memory — different thing). Editing a gold to reflect a schema change with the *faithful* value is standard.

Because the design-as-landed is the recommended design, the **orchestrator does not need to remediate** — land as-is.
