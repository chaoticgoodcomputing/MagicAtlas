## KEY FINDING — L02/L19 EquippedStateCharacteristic identity check (merge-reconciliation, NOT a FAIL)

L02 and L19 both add a new `EquippedStateCharacteristic` to `Characteristic.cs`. They are **NOT byte-identical — L19 is a strict superset of L02, with a latent fixture incompatibility a naive dedup would trip on**:

| | L02 (equipped-subtype-anthem) | L19 (equipped-creatures-keyword-list) |
|---|---|---|
| record | `sealed record EquippedStateCharacteristic : Characteristic;` (bare marker) | `... { public required bool Equipped { get; init; } }` |
| FromLabel | `"equipped" -> new EquippedStateCharacteristic()` | `"equipped" -> {Equipped=true}`, `"unequipped" -> {Equipped=false}` |
| schema Fields | `[]` | `["Equipped"]` |
| fixture emits | `{"CharacteristicType":"equipped"}` | `{"CharacteristicType":"equipped","Equipped":true}` |

Both use discriminator `"equipped"`, both cite CR 702.6 / 704.5n, both are rules-accurate in isolation. But L19 makes `Equipped` **required**, while L02's Kor Blademaster fixture omits it — so "keep either one" is unsafe:
- Keep L19's node -> L02's Kor Blademaster fixture fails to deserialize (missing required `Equipped`).
- Keep L02's node -> L19's Dalakos fixture carries an unknown `Equipped` field and loses the equipped/unequipped distinction.

**Safe merge (recommended):** adopt L19's superset node (bool `Equipped` + "unequipped" label) as canonical, drop L02's fieldless copy, AND add `"Equipped": true` to Kor Blademaster's equipped characteristic. (Alternatively make `Equipped` optional-defaulting-true so L02's fixture stays valid.) This is a mechanical dedup step, not a rules error — hence PASS on both branches with this flag surfaced.
